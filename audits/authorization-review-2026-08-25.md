# Authorization Implementation Review — CSPC-ICTU Monitoring System

**Date:** 2026-08-25
**Scope:** all **99 routes** across `backend/routes/*.js` (17 routers), `middleware/auth.js`,
`middleware/agentAuth.js`, and the service-layer reads behind them
**Companions:** `audits/api-infra-security-2026-08-25.md`, `audits/auth-flow-security-2026-08-25.md`
**Method:** every route enumerated programmatically with its guard chain (per-route *and*
router-level middleware), then the interesting ones read by hand and **probed unauthenticated
against the running backend**.

---

## 0. Verdict — Authorization: 8.5 / 10 → **9.5 / 10 after fixes**

**This is the strongest area of the codebase**, and the reason is structural rather than lucky:
authorization here has very little surface to get wrong. There is exactly one tenant, two roles,
and — critically — **almost no per-user data**. A server, a router, a UPS and an alert are shared
infrastructure that every ICTU staffer is *supposed* to see, so the classic BOLA/IDOR question
("is this row mine?") genuinely does not apply to most of the API. Where per-user data does
exist (notifications, the dashboard widget layout), the owner is taken from `req.user.id`
server-side and a client-supplied id is never consulted.

The enumeration is worth stating plainly, because it is the finding:

```
99 routes total
 ├─ 75  JWT required (33 of them additionally role-gated)
 ├─  2  agent bearer token (metric ingest)
 └─  5  deliberately unauthenticated  ← every one examined below
```

Of those five, four are structurally necessary (you cannot require a session on the endpoint that
*creates* the session). **One was neither necessary nor used** — that is AZ-01, and it is the only
real finding in this review.

| ID | Finding | Sev | CWE | Status |
|----|---------|-----|-----|--------|
| **AZ-01** | `GET /api/aircon/channels` — **unauthenticated, and called by nothing**; disclosed the AC inventory | **Low** | CWE-306, CWE-200 | ✅ **Fixed** |
| **AZ-02** | Reports are readable/downloadable by any authenticated staffer regardless of author | **Info** | — | ✅ By design — §5 |
| **AZ-03** | `GET /api/history` (audit trail, incl. others' IP + user-agent) is open to `it_staff` | **Low** | CWE-200 | ⏳ Accept or narrow — §6 |
| **AZ-04** | No `jti`; API tokens have no scopes | **Info** | — | ➖ N/A at this scale — §7 |

## 2. AZ-01 — Unauthenticated, unused AC config endpoint · **Low** · CWE-306, CWE-200

**Evidence (before):** `backend/routes/aircon.js:25-32`

```js
// ── GET /api/aircon/channels — ESP32 boot-time config fetch (no auth) ─────────
router.get("/channels", async (req, res, next) => {
  res.json(await airconService.getChannelConfig());
});
```

`getChannelConfig()` (`services/airconService.js:73-84`) returns every AC unit's **IR channel
number and current on/off state**.

**Why it matters.** The comment claims an ESP32 bootstrap, but **no client calls it**:

```
$ grep -rn "aircon/channels" iot/esp32/env_monitor_v2/*.ino      → (nothing)
$ grep -rn "aircon/channels" frontend/src/                        → (nothing)
```

The firmware receives the same payload as the **`irConfig` socket event**, on a connection
already authenticated with `DEVICE_SECRET` (`pushIRConfig` in this very file), and the dashboard
reads it from `GET /api/aircon/` behind a JWT. So the route served nobody while disclosing the
server room's AC inventory to anyone who could reach port 3000 — which, per
`api-infra-security-2026-08-25.md` A-03, is the whole campus LAN until the firewall rule lands.

Low severity: knowing that three AC units exist and unit 2 is on is not much of a prize. It is
listed because it is the **same shape** as the `/uploads` finding — a reader left behind after
its consumer went away — and because "unauthenticated endpoint nobody knows about" is precisely
the category that grows teeth when someone later extends it.

**Exploitability.** Unauthenticated GET, no rate-limit concern:

```
$ curl http://<host>:3000/api/aircon/channels
{"channels":[{"channel":1,"enabled":true},{"channel":2,"enabled":false}]}
```

**Fix — shipped.** Route removed; `getChannelConfig()` stays because `pushIRConfig` still uses it
for the authenticated socket push. The replacement comment records what it was, why nothing
needed it, and what to do if a future firmware genuinely wants an HTTP bootstrap (give it the
device-secret check the handshake uses — do not restore an open one).

**Verified:** `GET /api/aircon/channels` → **404**.

## 3. BOLA / IDOR — why most of it does not apply here, and where it does

The honest answer is that **this API has almost nothing to be BOLA'd**. Object-level
authorization asks "does this row belong to the caller?" — a question that only exists when rows
have owners. Here:

| Object | Owner | Object-level check needed? |
|---|---|---|
| `devices` (servers, routers, UPS, MikroTik, aircon) | none — shared campus infrastructure | ❌ Every staffer may see every device, by design |
| `alerts` | none — shared incident state | ❌ Explicitly shared (`alertsService` vs the per-user bell) |
| `alert_rules`, `aircon_ir_config` | none — global config | ❌ Admin-gated instead |
| **`alert_notifications`** (the bell) | **a user** | ✅ **Checked** |
| **`widget_prefs`** (dashboard layout) | **a user** | ✅ **Checked** |
| `reports` | an author, but shared by design | ⚠️ See AZ-02 |

**The two owned objects are correctly scoped — the owner comes from the verified token, never
from the request:**

```js
// routes/notifications.js — every call
notificationService.listForUser(req.user.id, …)
notificationService.markRead(req.user.id, ids ?? [])   // ids are filtered BY user inside
notificationService.clearAll(req.user.id)
notificationService.savePrefs(req.user.id, req.body ?? {})

// routes/widgetLayout.js
widgetPrefsService.getLayout(req.user.id)
widgetPrefsService.saveLayout(req.user.id, input)
```

There is **no route anywhere** that accepts a user id from the URL, body or query and acts on it
as the subject. The nine `/api/users/:id` routes are all `requireRole("admin")` — an admin acting
on another account is the feature, not a bypass — and `PATCH /users/me` derives its subject from
`req.user.id`, ignoring any id in the body.

**A detail worth crediting:** `POST /api/reports/:id/email` sends to
`{ toUserId: req.user.id }` — the recipient is the **caller**, not a client-supplied address. A
report-emailing endpoint that took a `to` field would be an open mail relay for exfiltration;
this one cannot be pointed at an attacker's inbox.

## 4. Privilege escalation — the paths that could grant a role, and why they don't

| Vector | Status |
|---|---|
| `role` in a self-update body | ❌ Impossible — `PATCH /users/me` passes `{ username: req.body?.username }` only |
| `role` in an admin update | ✅ Intended, and validated against the frozen `ROLES` allow-list |
| Setting your own `status` to `active` | ❌ No self-status route exists; `PATCH /users/:id/status` is admin-only |
| Self-approving a pending registration | ❌ A pending account cannot obtain a session at all (`sessionIsLive` requires `status='active'`), so it can never call the approve route |
| Forging `role` in the JWT | ❌ Signature + `iss`/`aud` verified; and **the role is now re-read from the database** on every request (auth-flow AF-04) |
| Mass assignment of `token_version` / `google_sub` | ❌ Every write destructures an explicit field list |
| Last-admin lockout / self-demotion | ✅ Guarded — `countOtherActiveAdmins` blocks demoting or disabling the final active admin |

**`requireRole` fails closed**, which makes middleware-ordering mistakes non-exploitable:

```js
function requireRole(...roles) {
  return (req, res, next) => {
    if (!req.user) return res.status(401).json({ error: "Unauthorized." });      // ← no authN ⇒ deny
    if (!roles.includes(req.user.role)) return res.status(403).json({ … });      // ← deny by default
    next();
  };
}
```

If `requireRole` were ever placed *before* `authMiddleware`, `req.user` would be undefined and the
request would be refused — not admitted. That is the correct failure direction, and it is why
item 12 (middleware ordering) passes structurally rather than by inspection alone. Every one of
the 33 role-gated routes was still checked: all order `authMiddleware → requireRole → handler`.

## 5. AZ-02 — Reports are shared, not per-author · **Info** · ✅ by design

`GET /api/reports/:id/download` is `authMiddleware` only, so **any** admin or it_staff may
download **any** report. `reportService.fileFor(id, format)` does not compare `generated_by`.

This is deliberate and documented: `GET /api/reports` returns everyone's reports, the list is
described as shared, and the lifecycle events (`reportCreated`/`reportUpdated`/`reportDeleted`)
broadcast to every dashboard. More to the point, **no privilege boundary is crossed**: a report
contains device telemetry both roles can already read live, so there is nothing in a report that
its downloader could not obtain from the API directly.

Left as-is. Downloads are audited (`action: "download_report"`) precisely because an export is
data leaving the system, which is the right control here — attribution rather than prevention.

`path.basename` + a `startsWith(REPORTS_DIR)` prefix check on the resolved path means `:id` cannot
be walked into an arbitrary file, and `format` is a two-value allow-list (`csv`/`pdf`).

## 6. AZ-03 — The audit trail is readable by `it_staff` · **Low** · CWE-200 · ⏳ your call

`routes/history.js:10` gates the whole router at `requireRole("admin", "it_staff")`.
`system_logs` is the table holding **`ip_address` and `user_agent`** — by the codebase's own
description, *"the most personal data in the schema"* — for **every** user, including admins.

So an it_staff account can read when each admin signed in, from which IP, on what browser. There
is no attack here; it is a disclosure question, and a reasonable one to answer either way:

- **Keep it open** — a five-person ICTU team where everyone troubleshoots, and the History page
  is a real operational tool. This is the current choice.
- **Narrow it** — one line, if ICTU would rather staff not see each other's addresses:

`historyService.getHistory` **already accepts a `userId` filter** — `routes/history.js:26`
forwards `req.query.userId` to it, which powers the page's per-actor dropdown. So narrowing is
genuinely two lines: stop taking that value from the client for non-admins, and pin it.

```js
// routes/history.js — inside the GET "/" handler
-       userId: req.query.userId,
+       // Admins may filter by any actor; everyone else is pinned to themselves, so the
+       // audit trail cannot be used to read a colleague's IP addresses and user-agents.
+       userId: req.user.role === "admin" ? req.query.userId : req.user.id,
```

⚠️ Doing this also **narrows the History page for it_staff**, who would no longer see aircon
toggles or alert acknowledgements by anyone else — which is arguably the page's whole purpose on
a shared-operations team. That is exactly why this is a policy call and not a bug fix: the
snippet is ready, the decision is ICTU's.

Worth raising with ICTU/DPO alongside the Privacy Notice review the project already owes, since
the notice is what discloses this retention and audience.

## 7. Scopes, tenancy, and the items that genuinely do not apply

**Multi-tenant isolation — N/A.** One tenant: CSPC-ICTU. No `tenantId` exists anywhere, so there
is nothing to inject or filter by, and no cross-tenant leak is possible. Multi-site scoping is a
known-unbuilt feature waiting on a second-campus decision; **if it is ever built, every query in
this API becomes a tenancy question at once** — that is the moment to re-run this review.

**API token scopes — N/A at this scale.** Three credential classes exist and they are already
separated by *route*, which is the coarse form of scoping:

| Credential | Accepted by | Can it reach anything else? |
|---|---|---|
| User JWT (`middleware/auth.js`) | 75 dashboard routes | No — `agentAuthMiddleware` never consults it |
| Agent token `AGT-` (`middleware/agentAuth.js`) | `POST /servers/metrics` + `/metrics/batch` **only** | No — it cannot read a single dashboard route |
| Install key `AIK-` | `POST /agents/register` only | No |
| `DEVICE_SECRET` | Socket.IO handshake only | No |

An agent token is therefore already least-privilege in the way that matters: a compromised agent
can post metrics for its own device and **nothing else** — it cannot list servers, read alerts or
touch a user. Adding a formal scope claim would add ceremony without changing that.

**Bulk endpoints — N/A/Pass.** The only batch route is `POST /servers/metrics/batch`, capped at
60 samples, and every sample is written under `req.device.device_id` from the **token** — the
per-item owner is not readable from the request body at all, so per-item ownership cannot be
spoofed. `POST /notifications/read` and `/clear` take id arrays, and both filter by
`req.user.id` inside the service rather than trusting the ids.

**Debug/seed/reset routes — none.** Searched for `/seed`, `/reset`, `/debug`, `/test-` and
`NODE_ENV`-conditional mounting across `routes/` and `src/`: no matches. There is no
environment-gated route in the codebase.

**CORS/CSRF — see the API audit.** No cookies anywhere, so CSRF is structurally N/A; CORS is an
explicit allow-list (`api-infra` A-06 covers the `*` guard rail).

**Open redirect — N/A.** No `next`/`redirect` parameter exists; post-login routing is client-side
to fixed paths.

## 8. Field-level authorization — no secret reaches a response

Checked every read path that touches a table containing credentials:

| Secret | Where it lives | Does it reach a response? |
|---|---|---|
| `mikrotik_devices.api_password` | AES-256-GCM at rest | **No** — appears only in `mikrotikPollerService` (the poller and the connection test), decrypted in-memory to build a connection object. No route selects it |
| `agent_tokens.approved_token_hash` / `_cipher` | hash + AES-GCM | **No** — `SERVER_SELECT` joins `agent_tokens` purely to filter `status='approved'` and selects no token column |
| `agent_install_keys.key_hash` / `key_cipher` | hash + AES-GCM | **No** — `BASE_SELECT` uses `k.*`, but `toClient()` re-projects to a whitelist and exposes only `canReveal: Boolean(r.key_cipher)` |
| `users.hash_password` | all-NULL (column now vestigial) | **No** — explicitly destructured away: `rows.map(({ hash_password, ...user }) => user)` |

The one endpoint that *does* return a credential — `GET /install-keys/:id/reveal` — is
admin-gated **and** audited (`action: "reveal_install_key"`), with the reasoning written down:
once keys are recoverable, "who looked at this credential" is the question the audit trail has to
answer. That is the right treatment.

⚠️ **`BASE_SELECT` using `k.*` is the one thing to keep an eye on.** It works only because
`toClient()` is disciplined. A future route that returns a raw row from that query would leak the
cipher. A `SELECT` naming its columns would make that impossible rather than merely unlikely.

## 9. Error handling & resource enumeration

Consistent, and the distinction is deliberate:

- **401** — no/invalid credential, or a dead session (`authMiddleware`).
- **403** — authenticated but wrong role (`requireRole`), or a rejected/pending/disabled sign-in.
- **404** — the object genuinely does not exist.

Because every object here is visible to every authenticated staffer, a 404 leaks nothing: there is
no "exists but not yours" state to confuse with "does not exist", which is the condition that
makes 403-vs-404 a disclosure problem elsewhere. `GET /api/servers/:id/logs` validates
`Number.isInteger(id)` and answers **400** on a non-numeric id — a shape error, not an existence
signal.

The central error handler gates 5xx text behind an explicit `expose` flag, so a driver message
naming a table cannot escape through an authorization failure.

## 12. What was verified, and what was not

**Verified:** all 99 routes enumerated programmatically with their full guard chains (per-route
and `router.use`); nine representative endpoints probed unauthenticated against the running
backend, each returning the expected 401/404/200; `getChannelConfig` confirmed to have no caller
in the firmware or the frontend before its route was removed; every credential-bearing table's
read path traced to confirm no secret reaches a response. 299/299 tests pass.

**Unable to verify — stated rather than assumed:**

- **Role enforcement was not exercised with a real it_staff session.** Proving 403-vs-200 end to
  end needs two live Google accounts at different roles. The guard chain is verified statically
  and `requireRole` is covered by its fail-closed structure, but no request was made *as*
  `it_staff` against an admin-only route.
- **Runtime route registration was not diffed against the static parse.** The parser reads
  source; `app._router.stack` at runtime would prove nothing is mounted dynamically. Nothing in
  `src/server.js` mounts conditionally, so the two should agree.
